면접에서 "어디서 막혔고 어떻게 풀었는지"를 바로 말할 수 있게 남기는 기록이에요. 막힌 순간에 바로 적고, 해결하지 못한 것도 남겨요.

## 작성 형식

```markdown
### T-001. 증상을 한 줄로
- 날짜 · 단계: YYYY-MM-DD · Python 송신부
- 증상: 무엇이 어떻게 보였는지 (수치·로그 포함)
- 가설: 원인 후보와 확인 순서
- 확인: 무엇을 측정하거나 읽어 봤는지 (소스 위치, 로그)
- 원인: 확정된 원인
- 해결: 무엇을 바꿨는지 (커밋 링크)
- 결과: 전후 수치 (예: 지연 ○○ms → ○○ms)
- 면접용 30초 버전: 상황 → 원인 → 해결 → 결과를 두세 문장으로
```

- [ ] 4. 추적 재획득 시 파티클 쓸림 — 필터 쪽은 리셋 구현·테스트 완료, 파티클은 3단계에서 확인

- [ ] 6. Python 재실행 후 복귀 실패 (seq) — 겪지 않음. 사전 설계(Idle 진입 시 seq 기준 초기화)로 예방했고, Unreal 헤드리스 실행에서 재실행 후 `Seq baseline 0` → 0.21초 뒤 Interactive 확인

### T-001. 카메라가 열리고 read()도 성공하는데 프레임이 전부 "카메라 꺼짐" 그림
- 날짜 · 단계: 2026-10-15 · Python 송신부 (D9 웹캠 협상 실측 중)
- 증상: MSMF로 1280×720을 열자 협상 결과가 1280×720@30.0이고, 실측 30.0fps에 read() 실패 0으로 "정상"처럼 보였어요. 그런데 연속 프레임 91개 중 90개가 바이트 단위로 같았고 평균 밝기가 0.2였어요. DSHOW로 바꿔도 같았어요 (9.2fps).
- 가설: ① 노트북 카메라 차단 키·렌즈 셔터 ② Windows 카메라 권한 거부 ③ 다른 앱 점유. 권한부터 확인하고, 다음으로 프레임 내용을 파일로 저장해서 눈으로 확인하는 순서로 봤어요.
- 확인: 레지스트리 `HKCU\...\CapabilityAccessManager\ConsentStore\webcam` 값이 `Allow`라 ②는 아니었어요. 프레임을 PNG로 저장해 보니 검은 바탕에 빗금 친 카메라 아이콘, 즉 드라이버가 만든 대체 이미지였어요.
- 원인: **삼성 노트북 설정의 "카메라 비활성"이 켜져 있었어요** (사용자 확인). 이 상태에서도 드라이버(Intel AVStream Camera)는 read() 성공과 정상 fps로 대체 이미지를 계속 보내요. Windows 개인 정보 설정의 카메라 권한(`Allow`)과는 별개의 OEM 스위치라서 권한 검사로는 잡히지 않았어요. 설정을 끈 뒤 1080p 실영상이 나왔어요.
- 해결:
  1. 사용자가 카메라를 켬
  2. 코드: 동일 프레임 감시 추가 — 16픽셀 간격 샘플이 1.0초 넘게 바이트 단위로 같으면 카메라 장애로 보고 프레임을 내보내지 않아요 → 송신이 멈춰서 Unreal은 "사람 없음"이 아니라 "파이프라인 중단(Idle)"으로 처리해요 (D11). `pose_osc/capture.py`, 테스트 `tests/test_capture.py`
- 결과: 카메라를 켠 뒤 사람 검출 80/80 프레임. 감시 로직은 가짜 카메라 테스트에서 "고정 이미지 → 송신 중단 → 영상이 바뀌면 재개"를 확인했어요. 덤으로, 이전에 잰 "DSHOW 9fps"도 대체 이미지로 잰 값이라 무효였어요 (실영상 재측정 47fps).
- 면접용 30초 버전: 웹캠이 read() 성공과 30fps를 보고하는데, 실제로는 "카메라 꺼짐" 그림만 보내고 있었어요. fps만 봤다면 정상으로 판단했을 텐데, 연속 프레임이 바이트 단위로 같은 걸 보고 찾았어요. 이 상태로 heartbeat를 보내면 Unreal이 "사람 없음"으로 오인하니까, 동일 프레임이 1초 이어지면 카메라 장애로 보고 송신을 끊어서 Idle 폴백이 걸리게 했어요.

### T-002. 1280×720 요청이 무시되고 1920×1080@60으로 열림
- 날짜 · 단계: 2026-10-15 · Python 송신부
- 증상: 실영상에서 요청 1280×720@30 → 협상 1920×1080@60.0 (MSMF). 60fps를 최대 속도로 처리하니 추론이 24~30ms, 송신이 32~40Hz로 들쭉날쭉했어요.
- 가설: ① `set()` 순서 문제 (FOURCC→크기→fps 순서가 중요하다는 사례가 있음) ② MSMF는 open할 때 파라미터로만 미디어 타입을 고름 ③ 카메라가 1080p 모드만 노출함
- 확인: 같은 카메라로 7가지 방법을 비교했어요.

  | 방법 | 결과 |
  |---|---|
  | MSMF, set 없음 / W·H·F / F·W·H / W·H | 모두 1920×1080, 약 60fps |
  | MSMF, open 시 파라미터 `[W, 1280, H, 720, FPS, 30]` | 1920×1080, 약 60fps |
  | DSHOW, set W·H·F | 1920×1080, 47fps (열기 2.16초) |
  | DSHOW, open 시 파라미터 | 1920×1080, 60fps |

- 원인: ③으로 추정해요 (어떤 방법으로도 1080p). 지원 모드 목록은 아직 직접 확인하지 못했어요. 확인 방법: Windows 카메라 앱 설정의 해상도 목록, 또는 `ffmpeg -f dshow -list_options true -i video="Intel(R) AVStream Camera"`.
- 해결: `--max-rate` 옵션을 추가해서 처리 주기를 30Hz로 고정하면 송신 30.0Hz, 추론 19~24ms, 캡처→송신 28~35ms예요. 1080p→720p 축소는 추론 비용 이득이 없어서(16.3ms vs 19.1ms) 쓰지 않아요. 사용자가 선택지 A(1080p@60 캡처 + 30Hz 처리)를 골라서 기본값을 30으로 바꿨어요 (DESIGN_DECISIONS D9 `변경` 메모).
- 결과: 30.0Hz, 유실 0 (수신 검사기 기준)
- 면접용 30초 버전: 사전 가설은 "720p에서 30fps가 안 나온다"였는데 실제로는 반대로, 카메라가 해상도 요청을 무시하고 1080p 60fps를 줬어요. set 순서와 백엔드를 바꿔 가며 7가지로 확인했고, 해상도를 줄여도 추론 비용이 안 줄어서 대신 처리 주기를 30Hz로 고정했어요. 60fps 입력은 처리 시점의 프레임을 더 새것으로 만드는 데 쓰였어요.

### T-003. 로그를 파이프로 받으면 출력이 깨지거나 죽음
- 날짜 · 단계: 2026-10-15 · Python 송신부
- 증상: 송신부 출력을 다른 프로세스로 받아 출력하던 스크립트가 `UnicodeEncodeError: 'cp949' codec can't encode character '—'`로 죽었어요.
- 가설: Windows에서 stdout이 콘솔이 아니면(파이프·파일) ANSI 코드페이지를 쓰는데, 한국어 Windows에서는 cp949이고 em dash(—)가 cp949에 없음
- 확인: 문제 문자가 U+2014. 콘솔에 직접 출력할 때는 문제없음 (Python이 콘솔에는 UTF-16으로 씀)
- 원인: 가설대로예요. 송신부 자체도 `| Tee-Object`로 로그를 저장하면 logging이 해당 줄을 버리고 "Logging error"를 찍게 돼요 (logging의 `handleError` 동작).
- 해결: 로그 문자열에서 em dash를 빼고, 송신부·수신 검사기 시작 시 `sys.stdout.reconfigure(errors="replace")`로 바꿨어요. 인코딩할 수 없는 문자는 `?`로 바뀌고 줄은 남아요.
- 결과: 파이프 출력 정상
- 면접용 30초 버전: 작은 건이지만, 시연 로그를 파일로 남기는 순간 깨지는 문제라 미리 막았어요.

### T-004. 미리보기를 켜면 추론이 2배 느려짐 (미해결)
- 날짜 · 단계: 2026-10-15 · Python 송신부
- 증상: `--max-rate 30 --preview`로 실행하면 처음 약 2초는 추론 21~24ms / 30Hz인데, 그 뒤로 50~53ms / 15~18Hz로 떨어졌어요 (두 번 연속 재현). 미리보기 없이는 30.0Hz, 19~24ms였어요.
- 가설과 확인 순서:
  1. 1080p 화면을 뒤집고 확대해서 그리는 비용 → 960 폭으로 줄여서 그려도 같았어요. 그리고 늘어난 건 그리기 시간이 아니라 **추론 시간 자체**(측정 구간에 그리기 미포함)라서 기각했어요.
  2. Windows 11 전원 스로틀링(EcoQoS) — 하이브리드 CPU(i7-13700H)에서 포그라운드가 아닌 창을 가진 프로세스를 효율 코어로 보냄 → `SetProcessInformation(ProcessPowerThrottling)`으로 해제하는 코드를 넣고 A/B 비교: 해제 14~16ms / 30Hz, 미해제 17~20ms / 30Hz. **둘 다 정상이라 재현에 실패**했어요.
  3. 배터리 절전 → AC 연결·충전 중이라 기각
- 원인: 미확정
- 해결: 미리보기 축소와 EcoQoS 해제를 예방 조치로 남겨 뒀어요 (해제는 `--allow-power-throttling`으로 끌 수 있음).
- 다음 확인: 2단계에서 Unreal을 포그라운드로 띄운 상태(실제 시연 조건)에서 `--allow-power-throttling` 유무로 추론 ms를 비교하고, 작업 관리자의 '효율 모드' 열도 함께 봐요.
- 결과: (미정)
- 면접용 30초 버전: 미리보기를 켜면 추론이 두 배로 느려지는 현상이 있었는데, 그리기 비용이 아니라 추론 시간 자체가 늘어난 걸 보고 OS 스케줄링 쪽(EcoQoS)을 의심했어요. A/B로는 아직 재현하지 못해서 원인은 미확정이고, 실제 시연 조건(Unreal 포그라운드)에서 다시 측정할 계획이에요.

### T-005. Unreal이 127.0.0.1로 보낸 패킷을 하나도 받지 못함
- 날짜 · 단계: 2026-10-15 · Unreal 수신부
- 증상: 수신 컴포넌트를 `127.0.0.1:8000`에 Listen시키고 Python이 127.0.0.1:8000으로 121개를 보냈는데, UE 로그에 `Seq baseline`도 상태 전환도 없었어요. `LogOSC: OSCServer ... started`는 정상으로 찍혔어요.
- 가설: ① 패킷 형식 문제 → 수신 검사기에서는 121/121 정상이라 기각 ② 바인딩 주소 문제 — D5 검증 중 `OSCServerReceiver.cpp`의 `SetAsLocalHostIfLoopback`을 읽다가 "루프백이면 로컬 호스트 주소로 바꾼다"는 코드를 미리 발견해 둔 상태였어요
- 확인: `GetLocalHostAddr()` 구현(`SocketSubsystemBSD.cpp:537`)을 보니 `-MULTIHOME`이 없으면 172.31.255.255로 UDP connect를 해서 나가는 인터페이스 주소를 돌려줘요. `netstat -ano -p UDP`로 보니 UE 프로세스가 `70.12.229.108:8000`(Wi-Fi IP)에 바인딩돼 있었어요.
- 원인: 엔진 OSC 플러그인이 루프백 주소를 LAN IP로 치환해서 바인딩해요. 127.0.0.1로 온 데이터그램을 받을 소켓이 없었던 거예요.
- 해결: `0.0.0.0` 바인딩 + 허용 송신자 `127.0.0.1` (사용자 선택, DESIGN_DECISIONS D3 `변경` 메모). 컴포넌트는 루프백 주소를 받으면 "실제로는 LAN IP에 바인딩된다"는 경고를 남겨요. 설정은 `Config=Game`이라 빌드 없이 바꿀 수 있어요.
- 결과: 수신 0/121 → 121/121, 0.2초 뒤 Interactive. 바인딩은 `0.0.0.0:8000`으로 확인.
- 면접용 30초 버전: 엔진 OSC 서버에 127.0.0.1을 줬는데 localhost 패킷을 하나도 못 받았어요. 플러그인 소스를 읽어 보니 루프백 주소를 LAN IP로 바꿔서 바인딩하고 있었고, netstat으로 실제 바인딩 주소를 확인했어요. 와일드카드에 바인딩하고 송신자 허용 목록을 localhost로 제한해서 해결했고, 이 설정은 추론 PC를 분리할 때도 허용 목록만 바꾸면 그대로 쓸 수 있어요.

### T-006. 두 수신기가 같은 포트를 동시에 잡고, 한쪽이 조용히 전부 가져감
- 날짜 · 단계: 2026-10-15 · Unreal 수신부 (T-005 해결 직후)
- 증상: Unreal이 `0.0.0.0:8000`을 잡은 상태에서 Python 수신 검사기를 `127.0.0.1:8000`으로 띄웠는데 둘 다 바인딩에 성공했어요. 패킷 121개는 전부 검사기로 갔고, Unreal은 0개였어요. **어느 쪽에도 오류가 없었어요.**
- 가설: Windows는 `SO_REUSEADDR` 없이도 와일드카드 바인딩과 특정 주소 바인딩의 공존을 허용하고, 더 구체적인 바인딩이 이긴다 (추측이었고 실측으로 확인하는 순서로 진행)
- 확인: `netstat`에 `0.0.0.0:8000`(UE)과 `127.0.0.1:8000`(python)이 동시에 보였어요. 수신 검사기 요약 121/121, UE 로그 수신 0.
- 원인: Windows의 바인딩 공존 규칙이에요 (플러그인 소켓은 `SetReuseAddr(false)`라도 `SO_EXCLUSIVEADDRUSE`가 아니라서 막지 못해요). 컴포넌트의 바인딩 사전 검사도 이 경우는 통과해요.
- 해결: 수신 검사기 기본 바인딩을 `0.0.0.0`으로 바꿔서 두 수신기가 같은 와일드카드를 다투게 했어요 (사용자 선택).
- 결과 (양방향 실측): UE 먼저 → 검사기가 `WinError 10048`로 바로 종료. 검사기 먼저 → UE가 `Receiver disabled: 0.0.0.0:8000 bind failed: SE_EADDRINUSE`. 조용한 실패가 시끄러운 실패로 바뀌었어요. 검사기에 `--host 127.0.0.1`을 직접 주면 다시 공존하니 `--help`와 README에 경고를 적었어요.
- 면접용 30초 버전: 같은 포트를 두 프로세스가 동시에 잡았는데 오류 없이 한쪽만 패킷을 받는 상황이 있었어요. Windows가 특정 주소 바인딩과 와일드카드 바인딩의 공존을 허용하기 때문이에요. 시연 중에 디버그 도구를 켜 두면 원인을 찾기 어려운 고장이 되니까, 양쪽 모두 같은 와일드카드에 바인딩하게 해서 충돌하면 바로 오류가 나도록 바꿨어요.
