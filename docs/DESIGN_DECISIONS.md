## 4. 결정 상세

### D0. 사전 결정 — 변경하지 않음

| 결정 | 이유 |
|---|---|
| 추론은 Unreal 바깥의 별도 Python 프로세스 | 장애 격리, 모델 교체 속도, 렌더와 GPU 경합 회피 |
| 전송은 OSC over UDP | 연속 좌표는 최신 값만 의미가 있어서 유실을 허용 |
| 수신 좌표는 최신 값만 게임 스레드에 전달 (큐에 쌓지 않음) | (보충) 오래된 좌표를 순서대로 처리할 이유가 없고, 쌓이면 지연이 누적됨 |
| Unreal 로직은 C++ 우선, 블루프린트는 Niagara 파라미터 연결 같은 얇은 층만 | (보충) 상태 로직을 코드로 두면 리뷰·디버깅·테스트가 쉬움 |

> "(보충)"은 원래 결정에 이유가 따로 적혀 있지 않아서 덧붙인 설명이에요.

### D1. 포즈 모델 — MediaPipe Pose Landmarker `확정·검증 필요`

| 선택지 | 장점 | 단점 |
|---|---|---|
| **MediaPipe Pose Landmarker (33점)** ← 채택 | 랜드마크마다 `visibility`·`presence` 점수 제공 → 신뢰도 폴백에 바로 연결. CPU 실시간 | 손가락 디테일 없음 (손목·검지·새끼·엄지 근사점 정도) |
| MediaPipe Hand Landmarker (21점 × 2) | 손 자체는 정밀 | 랜드마크별 신뢰도를 쓰기 어렵고 손 단위 점수 중심. 손이 프레임 밖으로 나가면 재검출 비용 |
| YOLO-pose (ultralytics, 17점) | GPU로 빠르고 다인원에 강함 | CUDA/torch 설치 부담이 1~2일 일정에 리스크. GPU로 돌리면 D0의 "렌더와 GPU 경합 회피"와 부딪힘 |

**채택 근거**: 요구사항의 "관절 신뢰도"가 모델 출력 필드(`visibility`)와 바로 대응해서, 폴백 판단 근거를 "모델 출력의 어떤 값"으로 명확히 설명할 수 있어요. CPU 추론이라 D0의 GPU 경합 회피 근거와도 맞아요.

**구현 메모**
- API는 레거시 `mp.solutions.pose`가 아니라 Tasks API(`mediapipe.tasks.python.vision.PoseLandmarker`)를 써요. 레거시는 지원 중단 방향이고, 최신 버전에서 완전히 제거됐는지는 설치할 때 확인해요.
- 모델은 `pose_landmarker_lite.task`로 시작하고, 떨림·누락이 심하면 `full`로 바꿔요.
- 사용 랜드마크는 손목 15(`LEFT_WRIST`)·16(`RIGHT_WRIST`)이에요. 신뢰도는 `visibility`를 기본으로 하고, `presence`도 로그로 남겨 비교한 뒤 확정해요 (§9).
- `num_poses = 1` — 단일 관람객 기준이고, 스키마의 `person`(0/1)과 맞춰요.
- 좌우 라벨: MediaPipe Pose의 LEFT/RIGHT는 화면 기준이 아니라 사람 기준으로 알고 있어요. 그래서 **이미지를 추론 전에 뒤집지 않고, 추론 후 좌표만 `x' = 1 − x`로 미러링**해요. 이미지를 먼저 뒤집으면 라벨이 반대로 붙을 가능성이 있어요 (실측으로 확인 — §8의 3번).
- Windows의 MediaPipe Python은 GPU delegate를 지원하지 않는 것으로 알고 있어서 CPU로 돌려요 (공식 문서로 확인 필요).

**면접 포인트**: 폴백 판단 근거를 모델 출력 필드로 설명할 수 있어요.

### D2. 캡처 지연 — 캡처 전용 스레드 + 최신 프레임 1칸 `확정`

**문제**: OpenCV `VideoCapture`는 드라이버·백엔드 버퍼에 프레임을 쌓아요. 추론이 프레임 간격(30fps 기준 약 33ms)보다 느리면 오래된 프레임을 처리하게 돼서 지연이 누적돼요.

| 선택지 | 특징 |
|---|---|
| `CAP_PROP_BUFFERSIZE = 1` | 한 줄로 끝나지만 백엔드(MSMF/DSHOW)에 따라 무시될 수 있음 |
| **캡처 전용 스레드 + 최신 프레임 1칸** ← 채택 | 항상 최신 프레임만 추론. 오래된 프레임은 덮어써서 버림 |
| Tasks API `LIVE_STREAM` 모드 | 비동기 콜백, 바쁠 때 프레임을 알아서 버림. 콜백 스레드 관리가 하나 더 생김 |

**채택 근거**: 파이프라인 입력(Python)과 출력(Unreal) 양 끝에 같은 "최신 값만" 원칙을 적용할 수 있어서, 하나의 설계 원칙으로 묶어 설명할 수 있어요.

**구현 메모**
- 추론은 `detect_for_video(image, timestamp_ms)`로 해요. 타임스탬프는 단조 증가해야 해서 캡처 시점의 `time.monotonic()`을 ms로 바꿔 쓰고, 같은 값을 One Euro의 dt 계산에도 써요.
- 같은 프레임을 두 번 추론하지 않도록 프레임 번호로 새 프레임인지 확인해요.
- 스레드 간 전달은 `threading.Condition`으로 해요. 튜플 하나를 통째로 교체하는 건 CPython에서 원자적이지만, 새 프레임이 올 때까지 바쁜 대기 없이 기다리려면 대기·통지가 필요해요.

**면접 포인트**: 입력·출력 양 끝에 같은 원칙(최신 값만)을 적용했어요.

### D3. OSC 메시지 스키마 — 프레임당 단일 메시지 `확정`

| 선택지 | 장단점 |
|---|---|
| 관절별 메시지 (`/hand/left`, `/hand/right`) | 단순하지만 왼손·오른손이 서로 다른 프레임 값으로 섞일 수 있음 |
| OSC Bundle | 원자성은 있지만 파싱이 복잡하고, UE 플러그인의 번들 처리 경로를 따로 확인해야 함 |
| **프레임당 단일 메시지** ← 채택 | UDP 데이터그램 하나가 곧 한 프레임. 받으면 전부, 잃으면 전부라서 찢어짐이 없음 |

**메시지 정의**

| 순서 | 이름 | 타입 | 의미 |
|---|---|---|---|
| 0 | `seq` | int32 | 송신 측 프레임 카운터 (프로세스 시작 시 0) |
| 1 | `person` | int32 | 0 = 사람 없음, 1 = 감지 |
| 2–4 | `lx` `ly` `lz` | float32 | 왼손(사람 기준). x·y는 정규화 [0, 1], x는 미러링 적용 후, y는 화면 위쪽이 0 |
| 5 | `lconf` | float32 | 왼손 신뢰도 [0, 1] |
| 6–8 | `rx` `ry` `rz` | float32 | 오른손, 규칙 동일 |
| 9 | `rconf` | float32 | 오른손 신뢰도 [0, 1] |

- 주소 `/dstrict/hands`, 타입 태그 `,iiffffffff`. 패킷 크기는 주소 16B + 타입 태그 12B + 인자 40B = **68바이트**라 UDP 데이터그램 하나에 분할 없이 들어가요.
- `z`는 MediaPipe의 상대 깊이(엉덩이 중점 기준, 작을수록 카메라에 가까움)라 범위가 [0, 1]로 고정되지 않고 신뢰도도 낮아요. 메시지에는 넣되 UE 매핑에서는 가중치 0으로 시작해요.
- **heartbeat**: 사람이 없어도 같은 주기로 보내요(`person = 0`, 신뢰도 0, 좌표 0). 그래야 Unreal이 "사람 없음 → 신뢰도 폴백"과 "파이프라인 중단 → 패킷 끊김 폴백"을 구분할 수 있어요.
- **seq**: 중복·역순 패킷을 버리고 유실률을 로그로 남기는 데 써요. localhost에서는 역순이 거의 없지만 비용이 int 하나라 넣어 둬요.
- **seq 재시작 규칙 (보강)**: Python을 다시 실행하면 seq가 0부터 시작해요. "이전 seq 이하면 버림" 규칙만 두면 재실행 후 패킷을 전부 버려서 시나리오 2(재실행 후 복귀)가 실패해요. 그래서 수신 측은 ① Idle 상태에서 첫 패킷을 받으면 seq 기준을 초기화하고, ② seq가 크게 역행하면(임계값은 §9) 송신 측 재시작으로 보고 초기화해요. 스키마는 바꾸지 않아요.
- **타임스탬프는 넣지 않아요**: 타임아웃 판단은 수신 측 단조 시계(`FPlatformTime::Seconds()`)만으로 충분해요. 게임 시간(`UWorld::GetTimeSeconds()`)은 일시정지·Time Dilation의 영향을 받아서 쓰지 않아요.
  - 정정 메모: 처음 정리할 때 "프로세스 간 시계 비교는 의미가 없다"고 적었는데, 같은 PC에서는 두 프로세스가 같은 하드웨어 카운터를 볼 수 있어서 과장된 표현이었어요. 정확한 근거는 "타임아웃 판단에는 송신 측 시계가 필요 없고, 추론 PC를 분리하면 시계 동기화 문제가 생긴다"예요. 지연 측정 방법은 §9에서 따로 정해요.
- 수신 시각은 게임 스레드에서 메시지를 처리한 시각이라 소켓 도착 시각과 최대 1프레임 차이가 나요. 타임아웃 단위(0.2~1.0초)에 비하면 무시할 수준이에요.
- 주소·포트는 기본 `127.0.0.1:8000`이고 양쪽 모두 설정으로 바꿀 수 있게 해요. 설치형 콘텐츠처럼 추론 PC를 분리하면 수신 측을 `0.0.0.0`으로 바인딩하고 방화벽 허용이 필요해요.

**면접 포인트**: heartbeat 하나로 두 폴백 조건("사람 없음"과 "파이프라인 중단")을 구분했어요.

### D4. 필터·상태 로직 위치 — 분리 `확정`

| 선택지 | 장단점 |
|---|---|
| 전부 Python | Unreal이 단순해지지만 튜닝마다 재시작이 필요하고, 패킷 끊김은 원리상 수신 측만 알 수 있음 |
| 전부 Unreal | 에디터에서 실시간 튜닝 가능. 하지만 One Euro는 샘플별 실제 dt가 필요한데 Unreal은 도착 시점만 앎 |
| **분리** ← 채택 | Python은 측정 노이즈 제거(One Euro), Unreal은 상태 판단 + 렌더 보간 |

**채택 근거**: 필터는 측정값의 성질(카메라 타임스탬프 기준)이고, 상태 판단은 수신 시점의 성질(타임아웃)이에요. 상태 머신을 한 곳(Unreal)에 모으면 디버깅이 쉬워요.

**EMA 대신 One Euro를 쓰는 이유**
- EMA는 계수 하나로 "떨림 ↔ 지연"을 고정된 비율로 맞바꿔요.
- One Euro Filter(Casiez, Roussel, Vogel, CHI 2012)는 속도에 따라 컷오프 주파수를 바꿔요. 느릴 때는 강하게 평활해서 떨림을 줄이고, 빠를 때는 약하게 해서 지연을 줄여요.
- 비용은 샘플당 O(1), 상태는 float 몇 개라 EMA와 사실상 같아요.
- 튜닝 순서(논문 권장): `beta = 0`으로 두고 손을 거의 멈춘 상태에서 떨림이 사라질 때까지 `min_cutoff`를 내려요 → 빠르게 움직이면서 지연이 줄어들 때까지 `beta`를 올려요. 미분 컷오프 `d_cutoff`는 1Hz로 고정해요.

**구현 메모**
- **재획득 시 필터 리셋**: 유효 샘플 사이 공백이 일정 시간을 넘은 뒤 다시 들어오면 필터를 첫 샘플로 초기화해요. 리셋하지 않으면 예전 위치에서 새 위치로 파티클이 쓸려 가요 (§8의 4번). 공백 기준값과 "유효 샘플"의 신뢰도 기준은 §9에서 정해요.
- 신뢰도가 낮은 샘플은 필터에 넣지 않아요. 그때 보내는 좌표는 수신 측이 신뢰도를 보고 무시해요.
- **Unreal 렌더 보간**: `alpha = 1 − exp(−dt / τ)` 형태의 지수 보간으로 프레임레이트에 독립적으로 만들어요. 30Hz 입력과 60~120Hz 렌더 사이의 계단 현상을 없애는 역할이에요. `FMath::VInterpTo`는 이동량을 `Clamp(dt × speed, 0, 1)`로 계산해서 엄밀히는 프레임레이트에 독립이 아니에요 (UE 5.x 소스 기준 기억 — 5.7 소스로 확인).

**면접 포인트**: 필터는 측정의 성질, 상태 판단은 수신의 성질이라 위치를 나눴어요.

### D5. Unreal 수신 구조 — A안 `확정·검증 필요`

**배경 (검증 필요)**: 엔진 OSC 플러그인은 UDP 수신 스레드에서 받은 패킷을 내부 큐에 넣고, 게임 스레드 Tick에서 큐를 비우면서 패킷마다 `OnOscMessageReceived`를 호출하는 구조로 기억하고 있어요. 그러면 플러그인 안에 이미 큐가 있어서 D0의 "큐에 쌓지 않음"과 부딪혀요. 5.7 소스에서 그대로인지 확인이 필요해요.

| 선택지 | 내용 | 장단점 |
|---|---|---|
| **A. 내장 플러그인 + 소비 측 덮어쓰기** ← 채택 | 델리게이트가 게임 스레드에서 오므로 핸들러는 멤버 1칸에 덮어쓰기만 하고 Tick에서 소비 | 동기화 코드 0, 구현이 빠름. 플러그인 내부 큐는 남음 (프레임당 패킷 1~2개라 실질 영향은 미미) |
| B. `FUdpSocketReceiver` 직접 사용 + 락 보호 최신 슬롯 | 수신 스레드에서 OSC를 직접 파싱하고 최신 값 1칸만 게임 스레드로 전달 | D0 그대로이고 멀티스레딩 소재로 강함. OSC 파싱을 직접 해야 해서 반나절 이상 소요 |
| C. A로 먼저 만들고 남는 시간에 B로 교체 | 수신부를 교체 가능한 경계 뒤에 둠 | 리스크는 낮지만 일정이 남아야 가능 |

**채택 근거**: 1~2일 일정의 핵심은 폴백 동작 시연이에요. "플러그인 내부에 큐가 있다는 걸 소스로 확인했고, 그래서 소비 측에서 최신 값으로 합쳤다"는 것 자체가 좋은 설명 소재가 돼요.

**D0과의 관계 (명시)**: D0의 "최신 값만 게임 스레드에 전달" 원칙은 **소비 측 기준**으로 지켜요. 플러그인 내부 큐는 남지만, 컴포넌트는 메시지를 쌓지 않고 1칸만 덮어쓰며 Tick에서는 그 1칸만 읽어요. B안은 시간이 남을 때의 교체 경로로 남겨 둬요.

**공통 규칙**
- `UOSCServer`는 `UPROPERTY(Transient)`로 붙잡아 GC에서 보호하고, `EndPlay`에서 명시적으로 `Stop()`과 델리게이트 해제를 해요. 소켓은 결정적으로 닫아야 하는 자원인데 UObject 회수 시점은 GC에 따라 비결정적이에요. 명시적으로 닫지 않으면 PIE를 빠르게 재시작할 때 이전 서버가 포트를 잡고 있어서 바인딩이 실패할 수 있어요 (가설 — §8의 2번). "UObject GC vs RAII" 차이가 실제로 드러나는 지점이에요.
- C++에서는 다이나믹 델리게이트(`OnOscMessageReceived`) 대신 Native 델리게이트(`OnOscMessageReceivedNative`)에 바인딩하는 쪽을 우선 검토해요. 다이나믹 델리게이트는 `UFUNCTION`과 리플렉션 호출을 거쳐요. 5.7에 Native 델리게이트가 있는지와 시그니처는 소스로 확인해요.
- 핸들러는 주소·인자 개수·타입을 검사하고, 맞지 않는 패킷은 버린 뒤 개수를 로그로 남겨요.
- 전송 계층(수신 컴포넌트)과 해석 계층(상태 머신)을 나눠서, 상태 머신은 "프레임 + 현재 시각"을 입력받는 형태로 둬요. 그러면 B안으로 바꿔도 상태 머신은 그대로예요.

**컴포넌트 형태**

| 선택지 | 장단점 |
|---|---|
| **ActorComponent** ← 채택 | 레벨별 설정, Details 패널 튜닝, Niagara와 같은 액터에 배치 가능 |
| WorldSubsystem | 배치가 필요 없지만 레벨별 튜닝이 불편함 |

**면접 포인트**: 플러그인 내부 큐를 소스로 확인하고 소비 측에서 최신 값으로 합친 과정, 그리고 GC와 결정적 자원 해제의 차이를 말할 수 있어요.

### D6. 상태 머신 `확정 (수치는 튜닝)`

**손별 (왼손·오른손 각각)**

| 상태 | 진입 조건 | 동작 |
|---|---|---|
| Tracking | 신뢰도 ≥ 0.6 | 목표 위치 갱신 |
| Holding | 신뢰도 < 0.4 | 마지막 유효 위치 유지, 타이머 시작 |
| Lost | Holding이 0.5초 넘게 지속 | 해당 손만 기본 연출로 전환 |

- 0.4~0.6 구간에서는 현재 상태를 유지해요 (값 히스테리시스).
- Holding이나 Lost에서 신뢰도가 다시 0.6 이상이 되면 Tracking으로 돌아가요.
- `person = 0`이면 두 손 모두 신뢰도 0으로 처리해요.

**전역**

| 상태 | 진입 조건 |
|---|---|
| Interactive | 패킷을 0.2초 동안 연속 수신 |
| Idle (비인터랙티브) | 마지막 패킷 이후 1.0초 경과 |

- 재진입에도 시간 히스테리시스(0.2초)를 둬서 간헐적인 끊김에 깜빡이지 않게 해요. "연속"의 판정 기준(허용하는 패킷 간 공백)은 §9에서 수치로 정해요.
- Idle로 들어가면 두 손은 Lost로, seq 기준은 초기화돼요 (D3).

**전환 연출**
- 상태 전환은 스냅하지 않고 가중치(전역 `InteractiveWeight`, 손별 가중치)를 0~1로 보간해서 Niagara에서 크로스페이드해요. 폴백이 "고장"이 아니라 "연출"로 보이게 하는 게 공간 콘텐츠에서 중요한 포인트예요.
- 위 수치는 모두 초기값이고 `UPROPERTY(EditAnywhere)`로 노출해서 튜닝해요.
- 상태와 전환 사유는 화면 디버그 표시로 확인할 수 있게 해요.

**면접 포인트**: 값 히스테리시스와 시간 히스테리시스를 함께 두고, 전환을 크로스페이드해서 폴백이 연출처럼 보이게 했어요.

### D7. 좌표 매핑 — 인터랙션 볼륨 `확정`

**채택 근거**: 공간 기반 콘텐츠는 관람객의 물리 공간을 가상 공간의 영역에 대응시키는 게 핵심이라고 봤어요. 미디어월이나 프로젝션 공간을 구성할 때와 같은 사고방식이에요. (이 문단은 설계 해석이에요.)

**매핑 규칙 (초기 제안 — 다음 세션에서 확정)**
- 미러링은 Python에서 끝내고(D1), Unreal은 축 매핑만 해요.
- 볼륨의 로컬 축 기준으로 매핑해서 박스 회전만으로 방향을 맞출 수 있게 해요. 관람 방향(카메라가 바라보는 방향)을 볼륨의 +X로 두면 정규화 x → 로컬 Y, 정규화 y → 로컬 Z(위아래 반전), z → 로컬 X(가중치 0으로 시작)예요.

**면접 포인트**: 카메라가 아니라 공간을 기준으로 매핑했어요.

### D10. 저장소 운영 `확정 (레포 생성 시 추가한 기본값)`

> 레포를 만들면서 새로 정한 항목이에요. 바꾸고 싶으면 **첫 `.uasset` 커밋 전에** 바꾸는 게 좋아요. 그 뒤에 LFS로 옮기려면 히스토리를 다시 써야 해요(`git lfs migrate`).

| 항목 | 선택지 | 채택 | 근거 |
|---|---|---|---|
| UE 바이너리 에셋 | Git LFS / 일반 Git | **Git LFS** (`*.uasset`, `*.umap`) | UE + Git 조합에서 가장 널리 쓰는 방식이에요. 바이너리는 diff·merge가 안 되고 수정할 때마다 히스토리에 통째로 쌓여요 |
| 모델 파일 `.task` | 커밋 / 다운로드 스크립트 | **커밋하지 않음** | 공식 다운로드 경로가 있어 재현 가능하고, 바이너리로 히스토리가 불어나는 걸 막아요 |
| 시연 영상 | 레포에 포함 / 외부 링크 | **외부 링크** | 용량과 LFS 대역폭 |
| 생성물 | — | 무시 | `Binaries`, `Intermediate`, `Saved`, `DerivedDataCache`, `.idea`, `.vs`, `*.sln`, venv 등은 엔진·IDE가 다시 만들어요 |

- LFS의 단점도 있어요. GitHub 무료 LFS에는 용량·대역폭 한도가 있고(현재 수치는 GitHub 요금 정책 확인), GitHub의 "Download ZIP"에는 기본적으로 LFS 실파일이 들어가지 않아요(레포 설정에서 켤 수 있음). 클라이언트에는 git-lfs가 필요한데 Git for Windows에는 기본으로 포함돼 있어요.

## 6. 장애 주입과 시연 시나리오

**Python 실행 옵션 (계획)**

| 옵션 | 동작 | 모사하는 상황 |
|---|---|---|
| `--drop-rate <0~1>` | 송신 패킷을 확률적으로 버림 | UDP 유실 |
| `--freeze-after <초>` | N초 뒤 송신 중단 | 파이프라인 중단 |
| `--noise <σ>` | 필터 **앞**에서 좌표에 가우시안 노이즈 추가 | 모델 출력 떨림 |

- 필터 on/off 전후 비교 방식(실행 옵션 vs 런타임 토글)은 §9에서 정해요.

**시연 시나리오**
1. 카메라를 손으로 가리기 → 신뢰도 폴백 (Holding → Lost → 기본 연출, 손을 떼면 복귀)
2. Python 프로세스 종료 → 1.0초 뒤 Idle, 다시 실행하면 0.2초 뒤 Interactive로 복귀
3. `--noise` 주입 → 필터 효과 전후 비교

## 11. 용어 메모

- **공식 용어**: OSC(Open Sound Control), UDP, One Euro Filter(1€ Filter), EMA(지수 이동 평균), 히스테리시스, Niagara User Parameter, ActorComponent, WorldSubsystem, UObject GC, RAII, NNE(Neural Network Engine)
- **개념적 표현** — 아래는 공식 용어가 아니라 이해를 돕기 위한 설명이에요.
  - "최신 값 1칸", "최신 값 덮어쓰기": 새 값이 오면 이전 값을 덮어쓰고, 소비하는 쪽은 가장 최근 값만 읽는 방식이에요. 비슷한 공식 용어로 이벤트 처리 분야의 coalescing(병합)이 있어요.
  - "heartbeat": 네트워크에서 널리 쓰는 관용 표현이고 OSC 표준에 정의된 메시지 유형은 아니에요. 여기서는 사람이 없어도 같은 메시지를 계속 보내 송신 측이 살아 있음을 알리는 용도예요.
  - "크로스페이드 폴백", 상태 이름 Tracking/Holding/Lost/Interactive/Idle: 이 프로젝트에서 붙인 이름이에요.
